# trading-gates — 交易決策閘門層（風險控制骨架）

把「AI/LLM 產生的交易訊號」接上真錢之前，先建立一層**確定性、可被稽核的閘門**。
本 repo 是那層閘門的骨架：一個 append-only 決策帳本、一組離線可驗證的測試、以及事後回驗腳本。

> 這不是交易策略。它不預測價格，也不產生進出場點。它只負責兩件事：
> **擋下不該執行的決策，並留下可回驗的紀錄。**

## 為什麼需要這一層

LLM 可以寫出看起來很合理的交易理由，但它沒有能力為自己的輸出負責：

- 它會被 prompt injection 影響
- 它會把「查不到資料」講成「一切正常」
- 它每次講的數字都不一樣，事後無法追溯

所以架構上必須三層分離，且**下單能力不得與推理放在同一層**：

| 層 | 內容 | 誰能改 |
|---|---|---|
| 推理層 | LLM 預測、critic 覆核 | 可被注入，一律假設不可信 |
| 確定性閘門層 | 純函式、常數寫死在模組內 | 不進 config、不進 DB、不由 LLM 產生 |
| 執行層 | 唯一下單入口 | LLM 沒有任何下單能力 |

自檢問句：**對這個 LLM 做 prompt injection，它能繞過哪一道閘門？** 答案必須是「沒有」。

## Fail-closed 紀律

這是整個 repo 的核心規則，違反它整套防護等於裝飾：

- 閘門遇例外、查不到資料、欄位不存在 → **一律視為 BLOCK**，並以 WARNING 以上記錄
- 禁止 `or True` / `and False` 出現在任何條件判斷（被遺忘的 debug 覆寫 = 永久失效的閘門）
- 禁止模組層（import 時）副作用：import 即執行會造成「有跑、無錯、無產出」
- 每個閘門都要有**負向測試**：餵一個確定不合格的輸入，確認它真的擋下

> 從未觸發的閘門，與永遠通過的閘門，在正式環境看起來一模一樣。

## 內容

```
decision_ledger.py      append-only JSONL 決策帳本（純 stdlib）
                        record / read_all / verify_entries / summarize / price_at_stock
weekly_verify.py        事後回驗：N 天後價格走勢 → 判對 / 賣早 / 未定 / unknown
test_decision_gates.py  353 行離線自測（零依賴、不連網、10 項斷言）
```

帳本只記**有決策**的事件：推播（`alert`/`tier`）、被擋（`dedup`/`data_fail`/`stale`）、
閘門判定（`gate`）與最終決策（`decision`）。不記每日「正常」——帳本要能一眼掃完。

回驗規則（`verify_mode`）：

- `down`（停損／停利類）→ 事後跌幅 ≥ band 記「判對」、漲幅 ≥ band 記「賣早」
- 未滿 horizon → `pending`；**取不到價 → `unknown`，不可算成判對**
- `abs`（區間／波動類）→ 任一向位移 ≥ band 才算兌現

## 快速開始

```bash
python3 test_decision_gates.py       # 零依賴，不連網，10 項斷言
```

```
$ python3 test_decision_gates.py
PASS  bar_age_days 過期判定
PASS  無效代號回 None（不拋例外）
PASS  保持續抱：達 1R → 停損上移到成本
PASS  全部資料失敗不得靜默
PASS  資料失敗必須入帳
SELFTEST PASS
```

## 設計筆記

- **入帳資格＝有可回驗的價格基準**。靜態參數品質類（例如「每格淨利夠不夠付手續費」）
  刻意不入帳——它與後續走勢沒有因果，寫進去只會稀釋判對率。
- **入帳失敗不得讓主流程崩潰**，但呼叫方必須在輸出裡講（帳本壞＝無法事後回驗）。
- **判據要標證據種類**：`[機制]`＝算術事實（費率、比率、門檻、實讀 vs 宣告落差）；
  `[現況]`＝描述當下結構（趨勢、波動、情緒）。閘門判據只能是 `[機制]`。
- 同一家族的反例：`if not enabled: return True`（閘門預設關閉）與
  「拿不到報價就放行」都是 fail-open，移植時要改成「拿不到資料就擋＋告警」。
